## NativePeers: native Claude/Codex/Antigravity CLI messaging and workers

Use NativePeers to contact another registered native Claude/Codex/Antigravity CLI conversation and to delegate focused implementation, debugging, tests, documentation, analysis or review to independent workers. Read the `nativepeers` skill at `/Users/danny/.agents/skills/nativepeers/SKILL.md`. The command is `/Users/danny/.local/bin/npeer`; the project is `/Users/danny/Documents/Tools/NativePeers`. Keep vendor-native tools available. NativePeers workers are separate native conversations with application-level parent links; they do not appear in the vendor's private subagent UI.

Delegate when a task has a clear boundary, needs an independent perspective or can run while the parent makes useful progress. Split parallel work by independent files/responsibilities; serialize overlapping edits or dependent steps. Keep small, immediate edits in the parent when delegation adds no useful parallelism. Follow the Model Selection section for allocation and cross-vendor review: a Claude-authored change gets a Codex reviewer, and a Codex-authored change gets a Claude reviewer. NativePeers supports implementation as well as review; choose the effective profile for the task.

- Run `npeer whoami --json` through this conversation's native shell tool before sending or spawning. Require its verified native UUID, owner and incarnation. `CALLER_UNBOUND` means this invocation lacks a verified session identity; do not invent one, borrow a binding, or choose a session by cwd/newest history. Existing sessions without hooks register on their next normal launch/resume; an untouched empty Codex TUI registers after its first native turn.
- Discover with `npeer list --json`. Resolve exact titles with `npeer resolve --to "claude:TITLE" --json` or `"codex:TITLE"` or `"antigravity:TITLE"`, then reuse the returned stable handle. Duplicate titles require choosing an explicit returned candidate. Never route by focused terminal, working directory or fuzzy title.
- Send with `npeer send --to HANDLE --message "TEXT" --client-request-id REQUEST_ID --json`; add `--request-reply` when an answer is needed. Reply with `npeer reply MESSAGE_ID --message "TEXT" --client-request-id REQUEST_ID --json`, using the immediate received message ID. Add `--request-reply` only when requesting another reply. Preserve each exchange separately. Controller completion notices carry group identity and attributed results; do not reply to them as if they were peers.
- Delegate with `npeer spawn --spec /absolute/path/batch.json --json`, or a bound namespaced `worker_spawn` tool when available. Copy and tailor `/Users/danny/Documents/Tools/NativePeers/examples/claude-to-two-codex.json` for two `gpt-6.1-sol`/`xhigh` workers, or `examples/codex-to-two-claude.json` under that same project for two Claude workers. Each worker accepts `model`: Claude `opus`, `sonnet` or a full native ID; Codex an exact catalog model plus `reasoning_effort`; Gemini uses `provider:"antigravity", model:"gemini-4-argon-high"` (template `examples/two-gemini-workers.json`). Omitted models resolve configured defaults once at spawn. Requested and observed models remain attributed, and follow-ups/resumes keep the observed model. Give each worker a distinct title and focused task, a fresh batch request ID, and explicit concurrency/depth/time limits. Do not substitute another requested model/effort. Use `permission_profile:"analysis"` with `workspace:{"mode":"inherit-read-only"}` for analysis; use `permission_profile:"workspace"` with `workspace:{"mode":"isolated-worktree"}` for edits. Grant `allow_sibling_messages:true` only for requested collaboration. Preserve separate results and inspect worker changes before any explicit merge.
- Choose the profile deliberately. Reading, analysis and review use `permission_profile:"analysis", workspace:{"mode":"inherit-read-only"}`. Implementation, fixes, test-writing and checks that need editing or command execution use `permission_profile:"workspace", workspace:{"mode":"isolated-worktree"}`. Tailor `/Users/danny/Documents/Tools/NativePeers/examples/implementation-workers.json`; its three providers are examples, not a requirement to launch all three. Claude, Codex and Gemini workers have each created and tested code concurrently in isolated worktrees.
- Before an editing spawn, check fresh `npeer whoami --json` profiles for `workspace`. Claude's native Bash pre-tool hook refreshes the actual mode because startup omits it. Plan mode remains analysis-only; older sessions may need their next normal launch/resume to load the hook. If `workspace` is missing, identify the current mode/binding/hook issue and report that specific limitation. Do not declare the whole machine read-only from an analysis template or stale startup grant, or change global permissions to force a grant.
- Give each worker a focused brief: the task, allowed files/responsibilities, relevant context, required checks and expected result. Use a shared exact baseline for parallel edits. Worktrees stay under `<source repo>/.worktrees/WORKER_ID`; dirty tracked changes are captured after baseline checks, and needed untracked files require an explicit `workspace.untracked_allowlist`. Do not copy secrets or whole parent histories. Keep work within the caller's returned limits and avoid two workers independently editing the same responsibility.
- Collect and integrate implementation results. Inspect each worker's native ID, requested/observed model, `changes.worktree`, `changes.patch_artifact`, changed/new-file lists and actual checks. Run the relevant integration checks and apply or merge the reviewed changes within the task's authorized scope, preserving unrelated source changes. NativePeers does not automatically merge. Continue through integration when implementation was requested; return patches alone only when that is the requested deliverable. Preserve unique worker changes until they are integrated or safely backed up. Never treat a submitted task, timeout or worker's unsupported claim as a verified result.
- After asynchronous dispatch, continue independent work or return for native completion. Use `npeer wait GROUP_ID --timeout-ms 30000 --on-timeout push --json` for a bounded current-tool wait, or `--on-timeout retain` to retain results. Read immutable results with `npeer result GROUP_ID --json`; do not spend model turns polling. A task-specific wait leaves the batch notification available. Report actual worker IDs/results; never answer delegated tasks on their behalf.
- Inspect with `npeer status HANDLE --json`; cancel only owned work with `npeer cancel HANDLE --reason "REASON" --json`. A task handle cancels that task; a group handle cancels the group. For released owned histories use `npeer resume-worker WORKER_ID --task-file /absolute/followup.txt --completion-mode wait --json`, or `npeer resume-command WORKER_ID --json` to obtain the exact manual command. Never start a second resume writer to inject into an existing live conversation.
- Choose a fresh client request ID for each new operation; reuse the original ID for retries. Queue acceptance is not model ingestion or a reply. Respect `HELD`, `SUBMITTED_UNCONFIRMED`, `DELIVERY_UNKNOWN` and exit 6: retain the IDs, inspect status, and reconcile rather than replaying a fresh copy. Native policy can hold, refuse or prompt; do not globally enable inbound acceptance, impersonate the human, change authentication, or widen permissions to force delivery.

The original daily-use hosts are eligible registered Claude interactive CLI, managed Codex standalone TUI and owned workers on this machine. Antigravity CLI now has exact caller registration, native analysis and implementation workers and a hook inbox for the next normal native invocation; it cannot wake an idle CLI. Prefer bounded waits for an Antigravity parent. See `docs/ANTIGRAVITY.md` for current live scope and shell limitations. The `gemini` shell command runs `agy --dangerously-skip-permissions`; `-c` continues, `-r TITLE|UUID` resumes exactly, and local `/rename TITLE` names a session. Startup naming and automatic picker opening are unavailable in CLI 1.4.5; do not pass slash text through `--prompt-interactive`. Private Desktop/T3 ingress and remote hosts are outside the verified mode. Preserve native homes, histories, authentication, existing tools, shell/YOLO behavior and `features.daemon_auto_start=false`. On `CAPABILITY_MISMATCH`, review the changed executable and the affected native integration before admitting it; do not bypass the compatibility check. Installation is not permission to override native policy, and verified core workflows are not a claim that every acceptance variant passed.

Full commands and limits: `/Users/danny/Documents/Tools/NativePeers/docs/USAGE.md`. Runtime/policy boundaries: `docs/RUNTIME.md` under that project. Current verification and remaining checks: `docs/VERIFICATION.md` and `evidence/acceptance.json` under that project. Keep provider execution and worker results native-backed; no tmux, typing injection, Herdr/T3 runtime dependency or permanent broker is needed.
