## NativePeers: native Claude/Codex/Antigravity CLI messaging and workers

Use NativePeers to contact another registered native Claude/Codex/Antigravity CLI conversation and to delegate focused implementation, debugging, tests, documentation, analysis or review to independent workers. Read the `nativepeers` skill at `/Users/danny/.agents/skills/nativepeers/SKILL.md`. The command is `/Users/danny/.local/bin/npeer`; the project is `/Users/danny/Documents/Tools/NativePeers`. Keep vendor-native tools available. NativePeers workers are separate native conversations with application-level parent links; they do not appear in the vendor's private subagent UI.

Delegate when a task has a clear boundary, needs an independent perspective or can run while the parent makes useful progress. Split parallel work by independent files/responsibilities; serialize overlapping edits or dependent steps. Keep small, immediate edits in the parent when delegation adds no useful parallelism. Follow the Model Selection section for allocation and cross-vendor review: a Claude-authored change gets a Codex reviewer, and a Codex-authored change gets a Claude reviewer. NativePeers supports implementation as well as review; choose the effective profile for the task.

- Run `npeer whoami --json` through this conversation's native shell tool before sending or spawning. Require its verified native UUID, owner and incarnation. `CALLER_UNBOUND` means this invocation lacks a verified session identity; do not invent one, borrow a binding, or choose a session by cwd/newest history. A native CLI launched inside an owned worker cannot borrow the outer bootstrap; use a separate owned delegation. Existing sessions without hooks register on their next normal launch/resume; an untouched empty Codex TUI registers after its first native turn.
- Discover with `npeer list --json`. Resolve exact titles with `npeer resolve --to "claude:TITLE" --json` or `"codex:TITLE"` or `"antigravity:TITLE"`, then reuse the returned stable handle. Duplicate titles require choosing an explicit returned candidate. Never route by focused terminal, working directory or fuzzy title.
- Send with `npeer send --to HANDLE --message "TEXT" --client-request-id REQUEST_ID --json`; add `--request-reply` when an answer is needed. Reply with `npeer reply MESSAGE_ID --message "TEXT" --client-request-id REQUEST_ID --json`, using the immediate received message ID. Add `--request-reply` only when requesting another reply. Preserve each exchange separately. Controller completion notices carry group identity and attributed results; do not reply to them as if they were peers.
- Delegate with `npeer spawn --spec /absolute/path/batch.json --json`, or a bound namespaced `worker_spawn` tool when available. Copy and tailor `/Users/danny/Documents/Tools/NativePeers/examples/claude-to-two-codex.json` for two `gpt-6.1-sol`/`xhigh` workers, or `examples/codex-to-two-claude.json` under that same project for two Claude workers. Each worker accepts `model`: Claude `opus`, `sonnet` or a full native ID; Codex an exact catalog model plus `reasoning_effort`; Gemini uses `provider:"antigravity", model:"gemini-4-argon-high"` (template `examples/two-gemini-workers.json`). Omitted models resolve configured defaults once at spawn. Requested and observed models remain attributed, and follow-ups/resumes keep the observed underlying model and Claude’s explicitly requested `[1m]` launch selection. The context modifier is not independently provider-observed. Worker leases pin the selected native provider home at spawn; defaults, restrictions, binding and resume all use that home. Use the returned `resume-command` with its `native_env` instead of constructing an ambient-home resume. Give each worker a distinct title and focused task, a fresh batch request ID, and explicit concurrency/depth/time limits. Do not substitute another requested model/effort. Use `permission_profile:"analysis"` with `workspace:{"mode":"inherit-read-only"}` for analysis; use `permission_profile:"workspace"` with `workspace:{"mode":"isolated-worktree"}` for Git edits or `workspace:{"mode":"isolated-copy","file_allowlist":["main.py"]}` for explicitly selected files in a non-Git project. Grant `allow_sibling_messages:true` only for requested collaboration. Preserve separate results and inspect worker changes before any explicit merge.
- Choose the profile deliberately. Reading, analysis and review use `permission_profile:"analysis", workspace:{"mode":"inherit-read-only"}`. Implementation, fixes, test-writing and checks that need editing or command execution use `permission_profile:"workspace", workspace:{"mode":"isolated-worktree"}`. Tailor `/Users/danny/Documents/Tools/NativePeers/examples/implementation-workers.json`; its three providers are examples, not a requirement to launch all three. Claude, Codex and Gemini workers have each created and tested code concurrently in isolated worktrees.
- Before an editing spawn, check fresh `npeer whoami --json` profiles for `workspace`. Claude's native Bash pre-tool hook refreshes the actual mode because startup omits it. Plan mode remains analysis-only; older sessions may need their next normal launch/resume to load the hook. If `workspace` is missing, identify the current mode/binding/hook issue and report that specific limitation. Do not declare the whole machine read-only from an analysis template or stale startup grant, or change global permissions to force a grant.
- Give each worker a focused brief: the task, allowed files/responsibilities, relevant context, required checks and expected result. Use a shared exact baseline for parallel edits. Worktrees stay under `<source repo>/.worktrees/WORKER_ID`; dirty tracked changes are captured after baseline checks, and needed untracked files require an explicit `workspace.untracked_allowlist`. Those selected files are frozen once per batch with content digests and modes; a changed source baseline is rejected before model admission. Do not copy secrets or whole parent histories. Keep work within the caller's returned limits and avoid two workers independently editing the same responsibility.
- Collect and integrate implementation results. Inspect each worker's native ID, requested/observed model, `changes.worktree`, `changes.patch_artifact`, changed/new-file lists and actual checks. Compare `changes.worker_delta_artifact` against the frozen input for worker-only edits; `changes.patch_artifact` reconstructs the whole final tree from baseline HEAD and includes inherited dirty edits. `worker_delta_empty:true` identifies a no-op. Inspect the retained worktree if a bounded patch is unavailable. Git renames retain both paths and built-in line-ending normalization is respected; a tracked custom Git filter can make the worker delta explicitly unavailable without executing that filter. Run the relevant integration checks and apply or merge the reviewed changes within the task's authorized scope, preserving unrelated source changes. NativePeers does not automatically merge. Continue through integration when implementation was requested; return patches alone only when that is the requested deliverable. Preserve unique worker changes until they are integrated or safely backed up. Never treat a submitted task, timeout or worker's unsupported claim as a verified result.
- After asynchronous dispatch, continue independent work or return for native completion. Use `npeer wait GROUP_ID --timeout-ms 30000 --on-timeout push --json` for a bounded current-tool wait, or `--on-timeout retain` to retain results. Read immutable results with `npeer result GROUP_ID --json`; do not spend model turns polling. A group wait claims every still-unsubmitted completion phase in its returned result, including phases added during the wait; an eligible singleton follow-up claims its own phase so a later automatic push does not duplicate the result. An initial task-specific wait leaves the batch notification available. Immutable `result` reads do not claim a notification. Report actual worker IDs/results; never answer delegated tasks on their behalf.
- Inspect with `npeer status HANDLE --json`; cancel only owned work with `npeer cancel HANDLE --reason "REASON" --json`. A task handle cancels that task; a group handle cancels the group. For released owned histories use `npeer resume-worker WORKER_ID --task-file /absolute/followup.txt --completion-mode wait --client-request-id REQUEST_ID --json`, or `npeer resume-command WORKER_ID --json` to obtain the exact manual command. Reuse that resume request ID with identical worker/text/completion arguments if its response is lost; it returns the original task without replay. Never start a second resume writer to inject into an existing live conversation.
- For a selected external brief or fixture, use `npeer artifact-add --file /absolute/path/brief.txt --json`, then give its immutable `artifact_id` only to the workers that need it through `context_refs`. Select nonsecret files deliberately; known credential paths and native transcripts are rejected, and prose is not scanned for secrets. No recursive import occurs. Workers can import only from their owned directory.
- Recover forgotten group IDs with `npeer groups --mine --limit 20 --json` and its `next_cursor`. This reads only the current parent’s retained delegations and does not claim completion. Export a granted patch or artifact with `npeer artifact-export ARTIFACT_ID --output /absolute/new.patch --json`; it creates a new file exclusively, verifies the digest and returns the worker-delta base when recorded. Inspect/apply it explicitly.
- Page an inbox with `npeer inbox --unread --page --limit 20 --json` and continue using `--cursor CURSOR` with the same selection. MCP `peer_inbox` has matching `unread`, `paged` and `cursor` arguments. Neither path exposes unconfirmed interactive bodies.
- For non-Git implementation, explicitly select focused nonsecret files with `workspace.mode:"isolated-copy"` and `file_allowlist`; the batch is limited to 256 files/10 MiB. Copies remain under `<source>/.worktrees/WORKER_ID` and return both patch views from their captured input. The source is never initialized as Git or edited by the worker. Check `docs/IMPLEMENTATION_WORKERS.md` for its verification scope.
- Use `npeer spawn --check --spec /absolute/batch.json --json` when inspecting selected homes/models/profiles and frozen input selection before launch. It reserves nothing, creates no workspace and submits no model input; any native metadata/catalog helpers are reported. A check cannot guarantee later entitlement or unchanged runtime/configuration.
- Use `npeer delta-preview WORKER_ID [--task-id TASK_ID] --json` before integrating a worker-only patch into source that may have changed. Inspect the frozen base, relevant input comparisons and bounded application check. It applies nothing and a clean check does not prove semantic correctness. Use `npeer cleanup --plan --limit 20 --json` or exact repeated `--worker-id` selections to inspect retained workspaces. The planner deletes nothing, refuses active/resumed generations, uncertain ownership and unique/unavailable changes, and requires a fresh check before any separately authorized removal.
- MCP-only workers/parents can use `peer_ack(message_id)` for an explicit model-reported processing acknowledgment and `task_groups(limit,cursor)` for their retained delegations. Neither proves native ingestion or claims completion. `result --include-artifacts` and MCP `task_result` with `include_artifacts:true` return at most 16 authorized first pages of 16 KiB; use the returned offsets or artifact export for more.
- For older uncertain delivery evidence, continue `npeer status MESSAGE_ID --refresh --scan-cursor CURSOR --scan-max-bytes 1048576 --json` (MCP `task_status`: `scan_cursor`, `scan_max_bytes`). Each window rechecks sender/recipient scope and reports exact inspected ranges; total reads are capped at 4 MiB including guards. Missing evidence is inconclusive and never permits replay. Antigravity worker readiness is rechecked for every fresh process, with current PID/start/native-UUID hook evidence. Conflicting ancestor hooks or same-name profiles fail readiness; native precedence remains unverified.
- Workers may supply optional fenced `nativepeers-result` JSON with `findings` and `tests_run` in their existing task. These are worker-reported claims, marked `independently_verified:false`; retain the raw result and independently run the relevant checks. Do not spend an extra model turn only to reformat a result.
- Choose a fresh client request ID for each new operation; reuse the original ID for retries. Queue acceptance is not model ingestion or a reply. Respect `HELD`, `SUBMITTED_UNCONFIRMED`, `DELIVERY_UNKNOWN` and exit 6: retain the IDs and use `npeer status MESSAGE_ID --refresh --json` as the recorded sender or recipient to inspect exact native ingestion evidence without resubmission. Missing history remains inconclusive. `ADMISSION_DEFERRED` is a definite pre-submission lock delay: retry the original request ID against its original target; never create a fresh copy or replay an uncertain attempt. A local timeout after native admission does not prove expiry or non-execution. Native policy can hold, refuse or prompt; do not globally enable inbound acceptance, impersonate the human, change authentication, or widen permissions to force delivery.

The original daily-use hosts are eligible registered Claude interactive CLI, managed Codex standalone TUI and owned workers on this machine. Antigravity CLI now has exact caller registration, native analysis and implementation workers and a hook inbox for the next normal native invocation; it cannot wake an idle CLI. Prefer bounded waits for an Antigravity parent. See `docs/ANTIGRAVITY.md` for current live scope and shell limitations. The `gemini` shell command runs `agy --dangerously-skip-permissions`; `-c` continues, `-r TITLE|UUID` resumes exactly, and local `/rename TITLE` names a session. Startup naming and automatic picker opening are unavailable in CLI 1.4.5; do not pass slash text through `--prompt-interactive`. Private Desktop/T3 ingress and remote hosts are outside the verified mode. Preserve native homes, histories, authentication, existing tools, shell/YOLO behavior and `features.daemon_auto_start=false`. Use `npeer doctor --json` for passive expected/current executable hashes and affected verification scope; it also reports selected-home owned hooks, profiles, skills, facade definitions and known disabled state without repair or inference. `PRESENT` does not settle native precedence or entitlement. Conflicting Antigravity workspace MCP definitions fail worker readiness; a global listing is not proof of the effective runtime tools. On `CAPABILITY_MISMATCH`, review the changed executable and the affected native integration before admitting it; do not bypass the compatibility check. Installation is not permission to override native policy, and verified core workflows are not a claim that every acceptance variant passed. Check current source/runtime scope in the verification record; historical PASS fields do not certify later code. When a provider is quota-limited, continue offline or with an explicitly selected available provider and retain the blocked provider check as BLOCKED.

Tailor `examples/claude-gemini-fallback.json` and inspect primary/alternatives with `spawn --check`.
